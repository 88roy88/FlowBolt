System map

Where does my request go?

Suppose you ask BuildApp to build a reading list. Three parts of the system work together before you see the first preview.

  1. Browser IDEYou type the request into chat. Nginx serves the IDE and forwards its chat connection to FastAPI.
  2. BackendFastAPI receives the message. The agent calls the model and sends progress events back to chat. Postgres stores chat history and run state.
  3. WorkspaceWhen the agent writes code, it writes files into the project’s workspace. Vite serves those files to the preview iframe.

Chat turns

What happens after I press Send?

A turn is one agent run. Asking for the reading list starts a turn. Approving its plan later starts another.

  1. Claim the projectBefore saving the request, the backend checks for an active run, unsaved edits or a version preview. If the checks pass, it claims the run in Postgres.
  2. Run and streamThe backend saves the prompt and starts the agent. Events update chat. A heartbeat tells other requests that the project is busy.
  3. Finish or stopOn success or failure, the backend attempts to commit changed files. Stop resets the workspace and trims agent output while keeping the request. The backend then releases the claim.

Agents

Which agent handles the request?

The router looks for a stored action_complete event. Until the first one exists, the router treats the project as new.

  1. First buildInterview mode can ask clarifying questions. Plan drafts the overview and waits for approval. Accepting starts Execute, which writes files and checks the build.
  2. Later editsOnce the first build completes, “Add a rating to each book” goes to FollowUp. It can inspect the workspace, edit files and reply directly.
  3. Reported errorsClicking Fix on an error starts FixError. Execute also has its own repair loop during the initial build.

Live preview

How does the preview stay current?

The preview is the running development copy of the app. Each active sandbox has its own directory and Vite server port.

  1. Start ViteOpening chat or the preview wakes the sandbox. A wake starts Vite if needed. An ordinary lookup refreshes the idle timer.
  2. Show an editThe iframe loads the app through the backend proxy. When Vite sends a hot update, the proxy takes the workspace lock before forwarding it to the browser.
  3. Return laterThe idle reaper can suspend the sandbox and release its port. The files stay on disk, ready for the next wake.

Versions

When does a change become a version?

The reading list has its own Git history. A read-only follow-up can answer a question without adding a version.

  1. Save changesAn agent turn that changes files can add a commit. If you edit files yourself, save or discard those edits before starting another turn.
  2. Preview a versionChoose an older commit to inspect it. Editing is blocked during preview. Exit preview to return to the latest version.
  3. Restore a versionRestore moves the project’s main branch back to the chosen commit and removes later chat events and messages.

Publishing

What do visitors get when I publish?

Publishing makes a build of the reading list available at a share link. Later workspace edits reach visitors when you publish again.

  1. BuildA user with publish permission starts a production build in the sandbox. The backend collects the output from dist/.
  2. UploadThe backend uploads the build to S3 under the project ID and saves the share handle, using the chosen slug or the project ID.
  3. ServeA visitor opens /shared/{handle}/. FastAPI resolves the handle and serves the published files from S3. The sandbox can be asleep.
